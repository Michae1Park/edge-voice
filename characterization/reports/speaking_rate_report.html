Interpretation

Bottom line

Accuracy fails long before hardware does. CPU tops out around 48% of one core and RSS never approaches a ceiling, even at 2× — but word error rate has already climbed to 1 in 4 by that point. For this pipeline, speaking rate is an accuracy problem first, and a resource problem never, within the range where the model still produces real output at all.

3× is not "the pipeline handles up to 3×, just less accurately" — it's a qualitatively different regime where the decoder stops doing the job and starts hallucinating. Nothing after that point should be read as a graceful degradation curve.

0.5×–2×: one clean, physical trend

the trustworthy range

Decode efficiency falls in a smooth, low-variance line — 3.67× → 2.08× → 1.62× → 1.38× audio-seconds decoded per second of compute. Compressing the same words into less audio doesn't shrink the decode workload proportionally, so the cost per second of (denser) content rises. CER tracks the same story: 0% → 3.9% → 25.2%, real substitution errors on genuinely fast speech, not truncation — the token budget was already scaled per condition to rule that out.

3×: a collapse, not a data point

phase-vocoder + decoder both give up

Raw transcripts show hallucination-style repetition ("저는 알고 있지만 저는 무서운 겁니다. 저는 알고 있지만…") and content that's wrong from the very first syllable, not just cut short. Latency, CPU, and decode-efficiency all look artificially better here — because the decoder is terminating early on audio it can't parse, not because the task got easier. Aggressive time-compression at this ratio also degrades the phase vocoder's own output quality, compounding the effect.

What stayed flat, and why that's not news

throughput ≈ 0.53× everywhere except 3×

Content-seconds-decoded-per-wallclock-second sat within a hair of 0.53× from 0.5× through 2×. That's the experimental control working, not a capacity finding: every file was built to exactly 60% occupancy regardless of speaking rate, specifically so density couldn't confound this result. At real-time playback, that metric is mechanically pinned near the occupancy target — it says nothing about decode capacity here.

Latency definition. End-to-end = time from an utterance's audio finishing ingest to its final transcript being published (VAD → STT → publish) — the same "mic-arrival → transcript" definition used elsewhere in this codebase's benchmarks.

Known limitation. The first counted segment of every run (excluded from all latency/decode-efficiency stats above) is occasionally corrupted by an unresolved warm-up/real-file boundary artifact in the test harness; it does not affect CER, throughput, CPU, or RSS.

RSS caveat. Resident memory rises smoothly across sequential runs within a single harness process regardless of condition — treat CPU as the reliable resource signal in this table; RSS mean is included for completeness, not as a speaking-rate finding.
