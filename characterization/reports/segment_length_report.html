Interpretation

Bottom line

This experiment can't cleanly isolate segment length, and that's the main finding. 2s.wav, 4s.wav, and 7s.wav are three different real recordings with different sentences — not the same content stretched to different lengths, unlike the speaking-rate test. So any pattern here is length and content entangled together, not length alone.

What it does show cleanly: the pipeline has comfortable decode headroom across this whole range (worst case still 2.16× real-time), and latency scales with real audio duration exactly as expected. Nothing here indicates a length-driven capacity risk between 2s and 7s.

Latency tracks duration cleanly

the one unsurprising number

605 → 1891 → 2731 ms tracks each recording's real length, consistent with the earlier 3s-vs-7s comparison: more audio to encode costs more decode time. No anomalies here.

4s is an outlier, not a midpoint

decode efficiency 2.16× (lowest) · CPU 28.0% (highest)

If duration alone drove these numbers, 4s should sit between 2s and 7s on every metric. Instead it's the worst on both decode efficiency and CPU — the most likely explanation is that 4s.wav's specific sentence is more demanding for the model or its VAD segmentation, not that 4 seconds is an intrinsically harder length. Unconfirmed without the raw per-segment data for this run.

Throughput stayed flat because there was headroom to spare

0.53× / 0.52× / 0.52×

Occupancy was held fixed at 60% for all three lengths — the same control used in the speaking-rate test — so throughput is mechanically pinned near that target regardless of length. It would only have degraded if decode efficiency dropped toward 1× and a backlog started forming; it never got close (2.16× even at its worst).

CER likely isn't measuring recognition difficulty

13.7% / 6.7% / 7.1% — worst at the shortest utterance

In the earlier 7s-only run, this same order-of-magnitude CER was traced entirely to a known warm-up-boundary artifact in the test harness — every real utterance there decoded at 0% error. CER being highest at 2s (the shortest reference) is exactly the pattern you'd expect if a fixed-size garbled artifact fragment dilutes more against a shorter reference text — not evidence that short utterances are harder to recognize. Not yet individually confirmed for 2s/4s.

Latency definition. End-to-end = time from an utterance's audio finishing ingest to its final transcript being published (VAD → STT → publish).

RSS caveat. Resident memory has previously been shown to climb smoothly across sequential runs within a single harness process regardless of test condition — treat the RSS row here as informational, not a length-driven finding, unless checked chronologically against run order.
